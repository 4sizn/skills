# /sdlc:requirements — SDLC 요구사항 정의

`$ARGUMENTS`

## 0. 규약 로드

`sdlc-waterfall` 스킬을 Skill 도구로 로드한다. 산출물 위치·frontmatter 스키마·완료 보고는 그 규약을 따른다.

## 1. 게이트

**없다.** 이 커맨드가 폭포수의 시작점이다.

## 2. 절차

### 2-1. 대상 저장소 확정

`git rev-parse --show-toplevel`로 산출물 루트(`<저장소 루트>/docs/sdlc/`)를 정하고 사용자에게 한 줄로 알린다.

- **여기가 의도한 프로젝트인지 확인한다.** 세션을 연 위치가 애매하면 묻는다 — 잘못 짚으면 엉뚱한 저장소에 산출물이 쌓인다.
- `docs/sdlc/`가 없으면 새로 시작하는 것이다 → `overview.md`를 `templates/overview.md.tmpl`로 먼저 만든다.
- 이미 `requirements.md`가 있으면 **덮어쓰지 않는다.** 갱신인지 새로 시작인지 사용자에게 확인한다.

### 2-2. 입력 수집

인자·대화 맥락에서 요구의 출처를 파악한다.

| 출처 | 처리 |
|------|------|
| Redmine 이슈번호 | **live 조회**한다. 기억·캐시를 쓰지 않는다. `issue_checked`에 조회 날짜를 적는다 |
| 문서·스펙 파일 | 읽고 근거로 삼는다. RVS 2.0이면 `raw/` 배치 여부를 확인한다 |
| 구두 설명 | 그대로 받되 출처를 `사용자 구두`로 표시한다 |

정보가 부족하면 **추측으로 채우지 않는다.** 무엇이 없는지 열거하고 사용자에게 묻는다.

### 2-3. 작성

`templates/requirements.md.tmpl`에서 출발한다. 이때:

- **모든 요구사항에 검증 가능한 수용 기준을 붙인다.** "잘 동작한다" 같은 판정 불가 기준을 쓰지 않는다.
- **Out of scope를 반드시 채운다.** 비어 있으면 범위가 정의되지 않은 것이다.
- 확인이 필요한 것은 `> [!question]`으로 남긴다. 답을 지어내지 않는다.
- Redmine 이슈 본문을 복제하지 않는다 — 링크 + 판정만.

### 2-4. 상태판 갱신

`overview.md`의 단계 상태판에서 요구사항 행을 갱신한다.

## 3. 마무리

`status: draft`로 저장하고 사용자에게 보고한다.

```
requirements.md 작성 완료 (status: draft)
  기능 요구사항 N건 · 비기능 N건 · 미확인 N건
  검토 후 승인하시면 status를 approved로 올리고 /sdlc:plan 으로 진행합니다.
```

**agent가 스스로 approved로 바꾸지 않는다.** 승인은 사람이 한다.

규약의 완료 보고 규격을 따른다 (RVS는 4블록).
